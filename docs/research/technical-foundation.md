# Техническая основа ВКР и план проверки реализуемости

Дата проверки источников: **15.11.2026**. Статус: исследовательская записка и проект технических решений. Стенд не развёрнут, совместимость компонентов и качество диагностики не измерены. Предложения ниже не являются результатами эксперимента.

## 1. Что уже даёт OpenTelemetry Demo

OpenTelemetry Demo подходит как инструментированное микросервисное приложение для внесения известных неисправностей. Для Kubernetes предусмотрен Helm chart; официальная страница указывает Kubernetes 1.24+, Helm 3.14+ и 6 ГБ свободной памяти для приложения. Это требования документации, а не измеренная потребность нашего стенда: дополнительно нужны ресурсы кластера, приложения ВКР и выбранных хранилищ. [Kubernetes deployment](https://opentelemetry.io/docs/demo/kubernetes-deployment/).

Документация Docker-варианта указывает Docker Compose 2+, 6 ГБ RAM и 14 ГБ диска; минимальный режим требует примерно 3 ГБ RAM, исключая Kafka и зависимые сервисы. Обычный `docker compose up` в актуальном описании не запускает весь стек наблюдаемости: нужно использовать описанный Make target или полный набор compose-файлов. Это относится к текущей документации, а не автоматически к любому старому релизу. [Docker deployment](https://opentelemetry.io/docs/demo/docker-deployment/).

| Компонент | Подтверждённое состояние / проектное решение |
| --- | --- |
| OTel Collector | Часть демо; маршрутизацию в собственные backend можно изменить через конфигурацию Helm. [Документация развёртывания](https://opentelemetry.io/docs/demo/kubernetes-deployment/) |
| Prometheus, Jaeger, OpenSearch, Grafana | Backend и интерфейсы штатного observability-режима в актуальной документации Docker. [Docker deployment](https://opentelemetry.io/docs/demo/docker-deployment/) |
| Loki, Tempo | Предложены в нашей концепции. Не считать установленными вместе с демо: нужно отдельно добавить и настроить экспорт, затем проверить данные. |
| Alertmanager | Предложенный источник алертов; наличие Prometheus само по себе не подтверждает готовую цепочку alert rule → Alertmanager → webhook нашего приложения. |
| Kubernetes API | Доступен при Kubernetes-развёртывании; собственному приложению потребуются клиент и права чтения нужных объектов. |
| Приложение ВКР, его MCP-сервер и хранилище запусков | Собственная разработка; в базовом демо их нет. |

У демо существуют встроенные feature flags для внесения неисправностей: например, `adFailure`, `adHighCpu`, `paymentFailure`, `paymentUnreachable`, `productCatalogFailure`, `recommendationCacheFailure`. Флаг `failedReadinessProbe` предназначен только для Kubernetes. `paymentUnreachable` меняет адрес вызываемого Payment в Checkout: эталонная причина должна отражать ошибку конфигурации вызова, а не утверждать, что сам Payment остановлен. [Feature flags](https://opentelemetry.io/docs/demo/feature-flags/).

Нельзя предполагать одинаковую полноту сигналов у всех сервисов. Матрица покрытия OTLP-логами прямо отмечает отсутствие экспорта у части компонентов; stdout и OTLP-логи также нужно различать. Для каждого выбранного сценария следует проверить, какие сигналы действительно поступают. [Log coverage](https://opentelemetry.io/docs/demo/telemetry-features/log-coverage/).

### Отдельно про готовый agentic mode

В актуальном Docker-описании есть `make start-agentic`, добавляющий Agent, MCP и Chatbot. Этот факт не означает наличия готового расследователя инцидентов. [Docker deployment](https://opentelemetry.io/docs/demo/docker-deployment/).

Agent обслуживает запросы пользователя через LangGraph ReAct и вызывает API магазина; по умолчанию использует записанные ответы LLM. MCP-сервис предоставляет операции магазина через обёртки над frontend API. Его инструменты нельзя автоматически использовать как провайдеры телеметрии нашей системы. Это пример интеграции MCP и наблюдаемости агентного приложения, а не подтверждённый аналог диагностики инцидентов. [Agent service](https://opentelemetry.io/docs/demo/services/agent/), [MCP service](https://opentelemetry.io/docs/demo/services/mcp/).

## 2. Предлагаемый минимальный стек

Для первого технического спринта предлагается сохранить направление Java/Kotlin + Spring из концепции, а число новых инфраструктурных компонентов ограничить.

| Слой | Предложение для проверки | Зачем |
| --- | --- | --- |
| Стенд | OTel Demo в локальном Kubernetes; фиксированный релиз/chart и values | Проверить выбранную целевую среду, сервисы и контролируемые сбои |
| Метрики | Штатный Prometheus | Проверить `MetricsProvider`, не разворачивая второе хранилище |
| Логи и трассировки | Сначала штатные OpenSearch и Jaeger; либо сразу Loki/Tempo, если это осознанно закрепим после оценки затрат | Отделить риск доступа к сигналам от риска замены backend |
| Диагностика | Одно Spring Boot приложение, общий интерфейс `DiagnosticStrategy` | Два алгоритма используют одинаковую инфраструктуру |
| LLM | Spring AI `ChatClient` / `ChatModel` за собственным `LlmGateway` | Сохранять запросы, ответы, фактическое число вызовов и usage |
| MCP | Небольшой отдельный Spring MCP-сервер с провайдерами, Streamable HTTP как кандидат транспорта | Проверить реальную клиент-серверную цепочку и нормализацию |
| Хранение | На spike JSON/JSONL-файлы в каталоге запуска; PostgreSQL после доказательства сквозного сценария | Не блокировать проверку алгоритмов проектированием БД |
| Запуск | Ручной POST/CLI с описанием алерта; затем правило Prometheus и Alertmanager webhook | Сначала проверить диагностику; отдельно доказать реальный вход от мониторинга |
| UI | Просмотр сохранённого результата/простой endpoint; полноценный интерфейс позже | Сделать ход расследования проверяемым уже в первом прототипе |

В принятом задании первыми интеграциями названы Prometheus/Alertmanager, Loki и Tempo. Основной план сохраняет это требование и включает установку и изменение Collector pipelines. Штатные Jaeger/OpenSearch можно использовать как временный контроль прохождения сигналов. Их использование вместо предусмотренных заданием интеграций потребовало бы отдельного согласования с руководителем; техническая записка сама по себе не меняет задание.

Spring AI предоставляет клиент LLM, сборку prompt и настройки модели; для MCP существуют клиентские и серверные Boot starters и Java SDK. Открытая документация при проверке отображала Spring AI 2.0.2; это версия страницы, не выбранная зависимость проекта. [ChatClient](https://docs.spring.io/spring-ai/reference/api/chatclient.html), [MCP overview](https://docs.spring.io/spring-ai/reference/api/mcp/mcp-overview.html).

MCP задаёт обмен контекстом между host/client/server, но не определяет алгоритм управления LLM и контекстом. Поэтому стратегии, ограничения и сохранение расследования остаются ответственностью приложения ВКР. Документация MCP меняется; версия протокола, реально поддерживаемая выбранным Java SDK, должна быть зафиксирована и проверена. [Architecture overview](https://modelcontextprotocol.io/docs/learn/architecture).

### Предлагаемые контракты инструментов

Начать с ограниченных операций, а не с универсального shell-доступа:

- `get_service_catalog(scope)` — сервисы/экземпляры и признаки сопоставления идентификаторов;
- `get_dependencies(scope, time_window)` — наблюдаемые связи и период наблюдения;
- `get_metrics(service_ids, metric_set, time_window, step, limit)`;
- `get_logs(service_ids, time_window, severity, trace_id, limit)`;
- `get_traces(service_ids, time_window, min_duration, error_only, limit)`.

Это проект интерфейсов, согласованный по именам с [формализацией алгоритмов](../design/diagnostic-algorithms.md). У каждого ответа нужны `query_id`, источник, фактическое окно, ограничения, признаки усечения, идентификаторы наблюдений и нормализованные записи. Статусы `ok/empty/partial/unavailable/timeout/invalid_query/not_captured` заданы в [модели данных](../design/problem-formalization.md). Имена метрик и доступные атрибуты следует установить по реальным данным. Prometheus предоставляет instant/range HTTP-запросы; в эксперименте всегда передаём явное время/окно, чтобы результат не зависел от текущего времени сервера. [Prometheus HTTP API](https://prometheus.io/docs/prometheus/latest/querying/api/).

В однократной стратегии MCP вызывает приложение по заранее заданному плану; модель получает уже подготовленный контекст и делает один диагностический вызов. В пошаговой стратегии приложение исполняет выбранные моделью допустимые запросы и управляет циклом. Нужно считать реальные обращения к модели: автоматический tool-calling и retry библиотек не должны незаметно превращать один вызов в несколько.

| 26–29 ноября | Сквозной запуск, ошибки и replay | Один сценарий проходит от описания алерта до протокола; повторный запуск на сохранённых данных не читает живые источники; отказ одного источника явно отражён в результате |

Критерии завершения spike:

- [ ] Есть воспроизводимое развёртывание с закреплёнными версиями; потребление ресурсов измерено на доступной машине.
- [ ] Получены метрики, логи и трассировки для выбранного сценария; проверены реальные labels, timestamps, trace ID и service ID.
- [ ] Известный сбой включён и выключен; записаны время, нагрузка и восстановление, без передачи эталона модели.
- [ ] MCP-клиент и MCP-сервер действительно обмениваются запросами; сохранены версия/транспорт и trace запросов.
- [ ] Сформирован ограниченный контекст и получен один результат LLM; ответ может быть неверным, его правильность ещё не критерий технической готовности.
- [ ] Сохранены все входные данные и протокол, достаточные для воспроизведения запуска; отсутствие данных отличается от ошибки источника.
- [ ] Выбран основной backend-стек и перечислены остающиеся ограничения.

## 4. Снимки данных и честное сравнение

Сохранение только готового prompt однократной стратегии недостаточно: пошаговая стратегия может запросить сведения, не попавшие в этот prompt. Предлагается до сравнения собрать общий ограниченный корпус телеметрии для разрешённого набора сервисов и окон. Обе стратегии работают с `ReplayProvider`, обслуживающим запросы из этого корпуса. Область корпуса фиксируется без знания ответов стратегий.

Предлагаемая структура экспериментального набора:

```text
experiment/<scenario>/<capture-id>/
  manifest.json             # версии, окна, схема, нагрузка, контрольные суммы
  incident.json             # наблюдаемый вход диагностики
  telemetry/                # исходные сигналы, страницы/выгрузки, статусы полноты
  normalized/               # нормализованные записи с evidence_id
  inventory.json            # состав сервисов на момент сбора
  graph.json                # наблюдаемые связи, окно и происхождение
  ground-truth.json          # эталон; НЕ доступен контексту или инструментам LLM
  runs/<strategy>/<run-id>/  # конфиг, запросы, ответы, usage, времена, результат
```

Если весь разрешённый корпус выгрузить нельзя, нужен изолированный восстановленный backend или явно ограниченный каталог воспроизводимых запросов. Ответ на отсутствующий в снимке запрос — `not_captured`, а не «данных нет»; такие запуски анализируются отдельно. Кэширование только фактически сделанных живых запросов не обеспечивает равные возможности двух алгоритмов.

Следует разделить две оценки:

1. **Качество и затраты алгоритма на сохранённых данных:** одна модель и её настройки, один корпус, одинаковый вход, заранее заданные бюджеты и несколько повторов. Протокол включает все диагностические вызовы, cumulative input/output tokens и результаты проверок доказательств.
2. **Работа интеграции на живом стенде:** задержки backend, ошибки сети, экспорт сигналов и webhook. Время replay-запроса нельзя выдавать за время получения данных из живого Prometheus/Jaeger/OpenSearch.

Времена сбора общего корпуса указываются отдельно. Для практической оценки однократного и пошагового вариантов включаем собственный сбор данных каждого запуска в end-to-end время. При исследовании равного бюджета различаем лимит одного контекстного окна и суммарный расход токенов всех шагов.

Модель не должна получать названия активированных feature flags, конфигурацию fault injection, эталон или список ожидаемых диагнозов. Общедоступные знания модели о Demo полностью исключить нельзя; ограничение необходимо описать. Один исходный сценарий может дать разные проявления при разной нагрузке, поэтому повторения одного снимка и независимые повторные внесения сбоя считаются разными уровнями повторяемости.

## 5. Из чего строить содержание диплома

Предлагаемая линия работы, согласующаяся с текущей темой:

1. Задача инженера: по наблюдаемому симптому локализовать источник и объяснить причину с указанием проверяемых свидетельств.
2. Обзор аналогов и ограничений: HolmesGPT и другие решения; отсутствие доказанной уникальности фиксируется прямо.
3. Формальная модель: инцидент, телеметрия, нормализация, доказательства, гипотеза, действие проверки, бюджет и результат.
4. Два алгоритма: фиксированный сбор и один диагностический вызов; адаптивный сбор для проверки гипотез с явными условиями остановки.
5. Реализация: провайдеры, MCP-контракты, оркестратор, ограничение контекста и хранение протокола.
6. Методика: сценарии с известными причинами, скрытый эталон, воспроизводимые корпуса, шкала оценки, повторения и анализ затрат.
7. Результаты: при каких условиях дополнительные шаги помогают, сколько стоят, какие ошибки остаются. Сейчас таких результатов ещё нет.

Самостоятельный вклад предлагается связывать с конкретной реализацией правил отбора и проверки гипотез и полученными экспериментальными выводами. Архитектурная интеграция LLM+MCP сама по себе не доказывает новизну. Достаточность выбранного вклада для требований ВКР согласуется с руководителем.

## 6. Неопределённости и решения после spike

| Вопрос | Как получить ответ |
| --- | --- |
| Достаточно ли ресурсов локального Kubernetes? | Измерить память/CPU/диск в здоровом и аварийном режиме; уменьшение состава стенда документировать |
| Оставить штатные backend или перейти на Loki/Tempo? | Сравнить трудозатраты интеграции и необходимые функции запросов; закрепить одно решение |
| Достаточна ли телеметрия для выбранных причин? | Вручную восстановить причину по тем же доступным данным до включения сценария в итоговый набор |
| Поддерживаются ли выбранные транспорт MCP и версия SDK? | Минимальный тест обнаружения и вызова инструмента, обработка timeout/error, сохранение версий |
| Работает ли structured output у выбранной модели? | Проверить схему результата и tool requests на нескольких пробных запусках; ошибки формата учитывать |
| Можно ли воспроизвести любой разрешённый запрос? | Проверить покрытие snapshot-корпуса и поведение `not_captured` |
| Какое реальное число сценариев и повторов доступно? | После пилота оценить стоимость и разброс; до итогового эксперимента зафиксировать протокол |

Все ссылки ведут на первичные источники. Страницы без закреплённого тега описывают актуальную документацию на дату просмотра и могут измениться. В коде и экспериментальном manifest требуется закрепление конкретных версий, а не ссылки на `latest`/`main`.
