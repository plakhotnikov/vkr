# Техническая основа ВКР и план проверки реализуемости

Источники проверены **15.11.2026**. Ниже предложены стек и проверки. Стенд не развёрнут; совместимость и качество не измерены.

## 1. Что уже даёт OpenTelemetry Demo

OpenTelemetry Demo предоставляет инструментированное приложение и Helm chart для Kubernetes. Документация требует Kubernetes 1.24+, Helm 3.14+ и 6 ГБ свободной памяти. Сверх этого нужны ресурсы кластера, приложения ВКР и хранилищ. Фактическое потребление предстоит измерить. [Kubernetes deployment](https://opentelemetry.io/docs/demo/kubernetes-deployment/).

Docker-вариант требует Docker Compose 2+, 6 ГБ RAM и 14 ГБ диска. Минимальный режим без Kafka и зависимых сервисов занимает около 3 ГБ RAM. В текущей документации полный стек запускается Make target или набором compose-файлов; одного `docker compose up` недостаточно. Для выбранного релиза это нужно сверить. [Docker deployment](https://opentelemetry.io/docs/demo/docker-deployment/).

| Компонент | Подтверждённое состояние / проектное решение |
| --- | --- |
| OTel Collector | Часть демо; маршрутизацию в собственные backend можно изменить через конфигурацию Helm. [Документация развёртывания](https://opentelemetry.io/docs/demo/kubernetes-deployment/) |
| Prometheus, Jaeger, OpenSearch, Grafana | Backend и интерфейсы штатного observability-режима в актуальной документации Docker. [Docker deployment](https://opentelemetry.io/docs/demo/docker-deployment/) |
| Loki, Tempo | Предложены в нашей концепции. Не считать установленными вместе с демо: нужно отдельно добавить и настроить экспорт, затем проверить данные. |
| Alertmanager | Предложенный источник алертов; наличие Prometheus само по себе не подтверждает готовую цепочку alert rule → Alertmanager → webhook нашего приложения. |
| Kubernetes API | Доступен при Kubernetes-развёртывании; собственному приложению потребуются клиент и права чтения нужных объектов. |
| Приложение ВКР, его MCP-сервер и хранилище запусков | Собственная разработка; в базовом демо их нет. |

Примеры встроенных feature flags: `adFailure`, `adHighCpu`, `paymentFailure`, `paymentUnreachable`, `productCatalogFailure`, `recommendationCacheFailure`. `failedReadinessProbe` работает только в Kubernetes. `paymentUnreachable` меняет адрес Payment в Checkout; эталонная причина здесь ошибка конфигурации вызова, не остановка Payment. [Feature flags](https://opentelemetry.io/docs/demo/feature-flags/).

Некоторые компоненты не экспортируют OTLP-логи. Stdout и OTLP-логи различаются; для каждого сценария нужно проверить поступление сигналов. [Log coverage](https://opentelemetry.io/docs/demo/telemetry-features/log-coverage/).

### Agentic mode

`make start-agentic` добавляет Agent, MCP и Chatbot. Готовой диагностики инцидентов это не даёт. [Docker deployment](https://opentelemetry.io/docs/demo/docker-deployment/).

Agent использует LangGraph ReAct и API магазина; по умолчанию ответы LLM записаны заранее. MCP оборачивает операции frontend API. Эти инструменты не являются провайдерами телеметрии для нашей диагностики. [Agent service](https://opentelemetry.io/docs/demo/services/agent/), [MCP service](https://opentelemetry.io/docs/demo/services/mcp/).

## 2. Предлагаемый минимальный стек

На первом спринте предлагается сохранить Java/Kotlin + Spring и ограничить число новых компонентов.

| Слой | Предложение для проверки | Зачем |
| --- | --- | --- |
| Стенд | OTel Demo в локальном Kubernetes; фиксированный релиз/chart и values | Проверить выбранную целевую среду, сервисы и контролируемые сбои |
| Метрики | Штатный Prometheus | Проверить `MetricsProvider`, не разворачивая второе хранилище |
| Логи и трассировки | Сначала штатные OpenSearch и Jaeger; либо сразу Loki/Tempo, если это осознанно закрепим после оценки затрат | Отделить риск доступа к сигналам от риска замены backend |
| Диагностика | Одно Spring Boot приложение, общий интерфейс `DiagnosticStrategy` | Два алгоритма используют одинаковую инфраструктуру |
| LLM | Spring AI `ChatClient` / `ChatModel` за собственным `LlmGateway` | Сохранять запросы, ответы, фактическое число вызовов и usage |
| MCP | Небольшой отдельный Spring MCP-сервер с провайдерами, Streamable HTTP как кандидат транспорта | Проверить реальную клиент-серверную цепочку и нормализацию |
| Хранение | На spike JSON/JSONL-файлы в каталоге запуска; PostgreSQL после доказательства сквозного сценария | Не блокировать проверку алгоритмов проектированием БД |
| Запуск | Ручной POST/CLI с описанием алерта; затем правило Prometheus и Alertmanager webhook | Сначала проверить диагностику; отдельно доказать реальный вход от мониторинга |
| UI | Просмотр сохранённого результата/простой endpoint; полноценный интерфейс позже | Сделать ход расследования проверяемым уже в первом прототипе |

Задание требует первых интеграций Prometheus/Alertmanager, Loki и Tempo. Нужно установить их и настроить Collector pipelines. Штатные Jaeger/OpenSearch могут временно проверять прохождение сигналов. Замена ими интеграций задания требует согласования с руководителем.

Spring AI предоставляет LLM-клиент, сборку prompt, настройки модели и MCP Boot starters; доступен Java SDK. При проверке страницы отображали Spring AI 2.0.2. Зависимость проекта ещё не выбрана. [ChatClient](https://docs.spring.io/spring-ai/reference/api/chatclient.html), [MCP overview](https://docs.spring.io/spring-ai/reference/api/mcp/mcp-overview.html).

MCP определяет обмен между host/client/server. Алгоритм, контекст, лимиты и протокол расследования реализует приложение. Версию протокола и её поддержку в Java SDK нужно закрепить и проверить. [Architecture overview](https://modelcontextprotocol.io/docs/learn/architecture).

### Предлагаемые контракты инструментов

Предлагаются типизированные операции без универсального shell-доступа:

- `get_service_catalog(scope)` — сервисы/экземпляры и признаки сопоставления идентификаторов;
- `get_dependencies(scope, time_window)` — наблюдаемые связи и период наблюдения;
- `get_metrics(service_ids, metric_set, time_window, step, limit)`;
- `get_logs(service_ids, time_window, severity, trace_id, limit)`;
- `get_traces(service_ids, time_window, min_duration, error_only, limit)`.

Имена согласованы с [алгоритмами](../design/diagnostic-algorithms.md). Ответ содержит `query_id`, источник, окно, ограничения, усечения, ID наблюдений и нормализованные данные. Статусы `ok/empty/partial/unavailable/timeout/invalid_query/not_captured` описаны в [модели](../design/problem-formalization.md). Метрики и атрибуты уточняются по реальным данным. Prometheus поддерживает instant/range HTTP-запросы; время и окно задаются явно для воспроизводимости. [Prometheus HTTP API](https://prometheus.io/docs/prometheus/latest/querying/api/).

Однократная стратегия вызывает MCP по плану приложения, затем один раз LLM. Пошаговая исполняет допустимые запросы модели в цикле. Считаются все реальные LLM-вызовы, включая автоматические tool-calling и retry библиотеки.

## 3. Что проверить 16–29 ноября

Предлагаемые проверки на 16–29 ноября:

| Период | Работа | Проверяемый результат |
| --- | --- | --- |
| 16–18 ноября | Зафиксировать окружение, релиз/chart, values и ресурсы; поднять Demo | Повторяемая инструкция запуска, список образов и версий; приложение отвечает, нагрузка проходит, телеметрия доходит до backend |
| 19–22 ноября | Получить данные из трёх источников и Kubernetes; проверить один известный сбой | Сохранены настоящие HTTP-запросы/ответы и нормализованные записи; сервисы сопоставлены между сигналами; видны здоровое и аварийное окна |
| 23–25 ноября | Подключить LLM и минимальный MCP-клиент/сервер | Вызов инструмента проходит из приложения через MCP к backend; один диагностический запрос возвращает результат со ссылками на предоставленные записи |
| 26–29 ноября | Сквозной запуск, ошибки и replay | Один сценарий проходит от описания алерта до протокола; повторный запуск на сохранённых данных не читает живые источники; отказ одного источника явно отражён в результате |

Критерии завершения spike:

- [ ] Есть воспроизводимое развёртывание с закреплёнными версиями; потребление ресурсов измерено на доступной машине.
- [ ] Получены метрики, логи и трассировки для выбранного сценария; проверены реальные labels, timestamps, trace ID и service ID.
- [ ] Известный сбой включён и выключен; записаны время, нагрузка и восстановление, без передачи эталона модели.
- [ ] MCP-клиент и MCP-сервер действительно обмениваются запросами; сохранены версия/транспорт и trace запросов.
- [ ] Сформирован ограниченный контекст и получен один результат LLM; ответ может быть неверным, его правильность ещё не критерий технической готовности.
- [ ] Сохранены все входные данные и протокол, достаточные для воспроизведения запуска; отсутствие данных отличается от ошибки источника.
- [ ] Выбран основной backend-стек и перечислены остающиеся ограничения.

## 4. Снимки данных и честное сравнение

Готового prompt недостаточно: пошаговая стратегия может запросить другие данные. До сравнения собирается общий корпус за разрешённые окна и сервисы. Обе стратегии используют `ReplayProvider`. Область корпуса фиксируется до их ответов.

Предлагаемая структура экспериментального набора:

```text
experiment/<scenario>/<capture-id>/
  manifest.json             # версии, окна, схема, нагрузка, контрольные суммы
  incident.json             # наблюдаемый вход диагностики
  telemetry/                # исходные сигналы, страницы/выгрузки, статусы полноты
  normalized/               # нормализованные записи с evidence_id
  inventory.json            # состав сервисов на момент сбора
  graph.json                # наблюдаемые связи, окно и происхождение
  ground-truth.json          # эталон; НЕ доступен контексту или инструментам LLM
  runs/<strategy>/<run-id>/  # конфиг, запросы, ответы, usage, времена, результат
```

Если корпус нельзя выгрузить полностью, нужен изолированный восстановленный backend или ограниченный каталог воспроизводимых запросов. Отсутствующий в снимке запрос возвращает `not_captured`; такие случаи анализируются отдельно. Кэш живых запросов одной стратегии не обеспечивает равных возможностей.

Оценки проводятся отдельно:

1. **На сохранённых данных:** одна модель и настройки, корпус, вход, бюджеты и повторы. Протокол содержит все вызовы, cumulative input/output tokens и проверки обоснованности.
2. **На живом стенде:** задержки backend, ошибки сети, экспорт и webhook. Время replay не заменяет время живого Prometheus/Jaeger/OpenSearch.

Сбор общего корпуса измеряется отдельно. В полное время каждого диагностического запуска входит его собственный сбор данных. Лимит контекста одного вызова отличается от суммарных токенов всех шагов.

Активные feature flags, fault injection, эталон и ожидаемые диагнозы недоступны модели. Её предварительные знания о Demo исключить нельзя. Нагрузка меняет проявление сбоя; повторы одного снимка и независимые внесения неисправности оцениваются отдельно.

## 5. Из чего строить содержание диплома

Предлагаемая структура диплома:

1. Задача инженера: по наблюдаемому симптому локализовать источник и объяснить причину с указанием проверяемых свидетельств.
2. Обзор аналогов и ограничений: HolmesGPT и другие решения; отсутствие доказанной уникальности фиксируется прямо.
3. Формальная модель: инцидент, телеметрия, нормализация, доказательства, гипотеза, действие проверки, бюджет и результат.
4. Два алгоритма: фиксированный сбор и один диагностический вызов; адаптивный сбор для проверки гипотез с явными условиями остановки.
5. Реализация: провайдеры, MCP-контракты, оркестратор, ограничение контекста и хранение протокола.
6. Методика: сценарии с известными причинами, скрытый эталон, воспроизводимые корпуса, шкала оценки, повторения и анализ затрат.
7. Результаты: при каких условиях дополнительные шаги помогают, сколько стоят, какие ошибки остаются. Сейчас таких результатов ещё нет.

Предлагаемый вклад: реализация правил отбора и проверки гипотез и экспериментальные выводы. Интеграция LLM+MCP сама по себе новизну не доказывает. Достаточность вклада нужно согласовать с руководителем.

## 6. Неопределённости и решения после spike

| Вопрос | Как получить ответ |
| --- | --- |
| Достаточно ли ресурсов локального Kubernetes? | Измерить память/CPU/диск в здоровом и аварийном режиме; уменьшение состава стенда документировать |
| Оставить штатные backend или перейти на Loki/Tempo? | Сравнить трудозатраты интеграции и необходимые функции запросов; закрепить одно решение |
| Достаточна ли телеметрия для выбранных причин? | Вручную восстановить причину по тем же доступным данным до включения сценария в итоговый набор |
| Поддерживаются ли выбранные транспорт MCP и версия SDK? | Минимальный тест обнаружения и вызова инструмента, обработка timeout/error, сохранение версий |
| Работает ли structured output у выбранной модели? | Проверить схему результата и tool requests на нескольких пробных запусках; ошибки формата учитывать |
| Можно ли воспроизвести любой разрешённый запрос? | Проверить покрытие snapshot-корпуса и поведение `not_captured` |
| Какое реальное число сценариев и повторов доступно? | После пилота оценить стоимость и разброс; до итогового эксперимента зафиксировать протокол |

Использованы первоисточники. Незакреплённые страницы описывают документацию на дату проверки и могут меняться. В коде и manifest нужны конкретные версии вместо `latest`/`main`.
