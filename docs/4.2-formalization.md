# 4.2. Формализация задачи диагностики

Пункт задания 4.2: модели телеметрии, граф зависимостей, нормализация, критерии качества, ограничения затрат.

Статус: черновик спринта 1 (16.11.2026). Критерии качества — в [4.8-evaluation.md](4.8-evaluation.md).

## 1. Инцидент

Инцидент — группа алертов из одного webhook Alertmanager:

$$I = (A, t_0, W, B)$$

- $A = \lbrace a_1, \dots, a_n \rbrace$, $a_i = (\text{name}_i, \text{labels}_i, \text{severity}_i, t^{start}_i)$ — алерты группы.
- $t_0 = \min_i t^{start}_i$ — начало инцидента.
- $W = [t_0 - \Delta_{before},\enspace t_{run}]$ — окно анализа. Ищем причину здесь.
- $B = [t_0 - \Delta_{before} - \Delta_{base},\enspace t_0 - \Delta_{before}]$ — базовое окно, «норма».

Правила:
- Запуск по webhook или вручную (сервис + время → один искусственный алерт).
- $t_{run}$ фиксируется при запуске. Окно потом не меняется. Повторы видят те же данные.
- $\Delta_{before}$, $\Delta_{base}$ — настройки (по умолчанию 15 мин, 1 ч). Подбор — в 4.8.

## 2. Модели телеметрии

Общий заголовок любой записи:
- $s = (\text{cluster}, \text{namespace}, \text{service})$ — сервис;
- $\rho = (\text{provider}, \text{query}, \text{rawId})$ — откуда и каким запросом получено.

| Тип | Запись | Источник |
|---|---|---|
| Метрика (ряд) | $m = (s, \text{name}, \text{unit}, [(t_k, v_k)], \rho)$ | Prometheus |
| Лог | $l = (s, t, \text{level}, \text{message}, \text{traceId}?, \rho)$ | Loki |
| Спан | $sp = (\text{traceId}, \text{spanId}, \text{parentId}, s, \text{operation}, t, \text{duration}, \text{status}, \rho)$ | Tempo |
| Событие K8s | $e = (s, t, \text{reason}, \text{message}, \rho)$ | Kubernetes API |

Набор метрик:
- Задан в конфиге шаблонами PromQL.
- По умолчанию на сервис: RED (rate, errors, duration p95/p99) + ресурсы (CPU, память, рестарты).
- В серии экспериментов одинаков для всех стратегий.
- Снимок конфигурации сохраняется с каждым запуском.

События K8s — отдельный тип. Деплой и OOMKilled — частые причины. В метриках видны плохо.

## 3. Граф зависимостей

$$G = (V, E)$$

Вершины $V$:
- сервисы из Kubernetes API (тип `service`);
- внешние зависимости из атрибутов клиентских спанов: база, Kafka, кэш (тип `infra`). Сами они спанов не пишут.
- Адрес из спана (`kafka:9092`) сопоставляется с Service в K8s. Не нашли — вершина «внешняя, не найдена в K8s».

Рёбра $E$:
- $u \to v$: «$u$ вызывает $v$». Только из трассировок. K8s API рёбер не даёт.
- Тип: `sync` (HTTP, gRPC) или `async` (через очередь, span links).
- Статистика ребра (вызовы, доля ошибок, p95) отдельно для $B$ и $W$.

Источник топологии — `TopologyProvider`:

| Реализация | Откуда | Когда |
|---|---|---|
| `ServiceGraphTopologyProvider` | Метрики графа сервисов (`traces_service_graph_request_total{client, server}`) из OTel Collector `servicegraph` или Tempo metrics-generator, за период $T_G$ (24 ч) | Основной |
| `StaticTopologyProvider` | Граф описан вручную (YAML, каталог сервисов) | Нет трассировок |
| нет | $E = \varnothing$, только вершины из K8s | Ничего нет |

- Свою агрегацию спанов не пишем: дублирует `servicegraph`. Есть трассы без графа — включить connector в Collector.
- Виртуальные вершины для Kafka и Postgres на OpenTelemetry Demo — [проверить на стенде, спринт 2].
- Граф неполный: часть вызовов не трассируется. Фиксируем как ограничение.
- Провайдер топологии пишется в протокол запуска. Наличие графа — ось эксперимента.

## 4. Нормализация и фильтрация

Нормализация (из [заметок](../vkr_concept_notes.md)):
- время — UTC, исходное сохраняется;
- сервис — общий идентификатор $s$, соответствия в конфиге;
- trace ID и request ID сохраняются;
- происхождение $\rho$ сохраняется;
- не смогли определить сервис или связь — помечаем.

### Зачем фильтрация

Сырых данных слишком много. За 15 минут у одного сервиса — тысячи строк логов, сотни точек метрик, тысячи спанов. В LLM это не влезет и утопит главное.

Фильтрация сжимает сырые данные в **сигналы**: короткие сообщения «вот что странно».

### Сигнал

$$\varepsilon = (s, \text{type}, \text{summary}, \text{score}, \rho)$$

| Поле | Что это | Пример |
|---|---|---|
| $s$ | Сервис | `payment` |
| type | Откуда сигнал: метрика, лог, спан, событие K8s | `log` |
| summary | Сводка одной строкой — её читает LLM | «новый шаблон "charge failed": 2 300 раз за 15 мин, в норме 0» |
| score | Балл странности от 0 до 1. 0 — как обычно, 1 — очень странно | 0.95 |
| $\rho$ | Происхождение: откуда и каким запросом достали (раздел 2). По нему проверяем ссылки и открываем исходные данные | Loki, `{service="payment"} \|= "charge failed"` |

Правила:
- Балл всегда от 0 до 1 — чтобы сравнивать сигналы разных типов при упаковке в лимит ([4.4](4.4-algorithms.md)).
- Странность = отличие окна $W$ от нормы $B$. Без нормы не понять: 200 мс — много или как всегда.
- $W$ и $B$ разной длины (15 мин и 1 ч). Счётчики сравниваем **в минуту**, не в штуках.
- Фильтрация не знает лимитов. Одинакова для всех стратегий (кроме S2 — там её нет).

### По типам данных

#### Метрика

- **Вход:** ряд точек из набора метрик за $W$ и $B$.
- **Делаем:** вместо точек — сводка: «норма X, в окне Y, отклонение с момента t».
- **Балл:** насколько типичное значение в окне ушло от нормы, в «нормальных разбросах».

$$z = \frac{\text{median}_W - \text{median}_B}{1.4826 \cdot \text{MAD}_B + \epsilon}, \qquad \text{score} = \min\left(1, \frac{\lvert z \rvert}{2\theta}\right)$$

- median — середина значений. MAD — типичный разброс вокруг середины. Множитель 1.4826 делает MAD сравнимым с обычным стандартным отклонением.
- Почему не среднее: один выброс в норме ломает среднее, медиану — нет.
- $\epsilon$ — маленькое число, чтобы не делить на ноль, если в норме метрика стояла ровно.
- $\theta$ — порог. При $\lvert z \rvert = \theta$ балл 0.5; при $2\theta$ и больше — 1. Ниже порога сигнал не создаём.
- Пример: задержка p95 в норме 120 мс ± 10, в окне 480 мс → $z$ ≈ 24 → балл 1. Сводка: «p95 120 → 480 мс с 14:02».

#### Лог

- **Вход:** строки логов уровня WARN и выше (предупреждения и ошибки) за $W$ и $B$.
- **Делаем:** группируем похожие строки в шаблоны алгоритмом Drain (He et al., 2017). «Timeout to 10.0.0.5» и «Timeout to 10.0.0.7» → один шаблон «Timeout to <*>». На шаблон: сколько раз в минуту в $W$, сколько в $B$, 1–2 примера строк.
- **Балл:**
  - шаблона не было в $B$ (новая ошибка) → 1;
  - был → по росту частоты: $r = \dfrac{\text{rate}_W + 1}{\text{rate}_B + 1}$, $\text{score} = \min\left(1, \dfrac{\log_2 r}{k}\right)$. «+1» — чтобы не делить на ноль. $k$ — настройка: во сколько раз «вырос вдвое» должно считаться очень странным.
  - частота не выросла → сигнал не создаём.
- Пример: «charge failed» — в норме 0, в окне 150 в минуту → новый шаблон → балл 1.

#### Спан

- **Вход:** спаны из Tempo за $W$, статистика по операциям за $B$.
- **Делаем:** берём только плохие спаны: с ошибкой или медленнее p99 этой операции в норме (p99 — время, быстрее которого проходят 99% запросов). Группируем по рёбрам графа: «checkout → payment». На ребро: доля ошибок, задержка, 2–3 примера trace ID.
- **Балл:** больший из двух:
  - рост доли ошибок: $\text{err}_W - \text{err}_B$ (доли от 0 до 1);
  - рост задержки: $\min\left(1, \dfrac{\log_2 (p95_W / p95_B)}{k}\right)$.
- Пример: checkout → payment, ошибок 0% → 30% → балл 0.3; задержка не выросла.

#### Событие K8s

- **Вход:** события Kubernetes за $W$: рестарты, деплои, OOMKilled, проваленные проверки готовности.
- **Делаем:** берём все. Их мало.
- **Балл:** по типу события, из конфига. Например: OOMKilled, CrashLoopBackOff — 1; деплой новой версии — 0.8; проваленная проверка готовности — 0.6; прочее — 0.3.

### Настройки

$\theta$, $k$, веса событий K8s — настройки. Подбираются без LLM на тренировочных сценариях ([4.8](4.8-evaluation.md), раздел 4).

## 5. Ответ системы

Ответ — 3 гипотезы, от самой вероятной:

$$H = (h_1, h_2, h_3, \text{missing})$$

$$h_j = (s_j, c_j, \text{subtype}_j, \text{explanation}_j, \text{evidence}_j, \text{recs}_j)$$

- $s_j$ — сервис-виновник.
- $c_j$ — группа причины из списка (~8, в конфиге).
- $\text{subtype}_j$, $\text{explanation}_j$ — своими словами.
- $\text{evidence}_j$ — номера сигналов (`S7`) или вызовов инструментов (`R3`).
- $\text{recs}_j$ — 1–3 рекомендации: (тип «проверить» | «исправить», действие, ссылки).
- $\text{missing}$ — чего не хватило: «трассировки недоступны» и т. п.

Группы причин (уточнить под сценарии стенда):
1. закончились ресурсы (CPU, память, OOM);
2. зависимость недоступна или отвечает ошибками;
3. ошибка в коде сервиса;
4. рост задержки (сеть, медленная зависимость);
5. проблема с очередью сообщений;
6. неудачный деплой или изменение конфигурации;
7. перегрузка трафиком;
8. другое.

Почему ~8, не 30: группы не пересекаются, модели проще выбрать, на 15–20 сценариев по 2–3 на группу. Разнообразие из жизни — в подтипе.

Система рекомендации не выполняет.

## 6. Ограничения затрат

Лимит на один запуск:

$$\beta = (T_{max}, N_{max}, C_{max})$$

- $T_{max}$ — время от начала сбора данных до ответа.
- $N_{max}$ — число запросов к LLM. У однократной стратегии всегда 1.
- $C_{max}$ — **сумма** входных токенов по всем запросам запуска. Пошаговая шлёт историю заново, поэтому считаем сумму.

Как соблюдаем:
- Входные токены ограничиваем сами: считаем токенизатором до отправки, лишнее не кладём.
- Длину ответа — параметром `max_tokens` API.
- Пошаговая держит запас на последний запрос «дай финальный ответ».
- Токены — жёсткий лимит. Время — мягкий: новых шагов не начинаем, просим финальный ответ.
- $C_{max}$ ниже окна контекста модели.

Как меряем:
- Токены — из блока `usage` в ответе API.
- Все вызовы LLM, включая HolmesGPT, идут через один LLM-прокси (например, LiteLLM Proxy) [проверить подключение HolmesGPT, спринт 2].
- Время — свои замеры: отдельно сбор данных и ожидание LLM.
